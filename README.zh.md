# DSH 工作台布局

**简体中文** | [English](README.md)

为 DeepSeek Harness Web 提供三栏工作区：左侧导航、中间文件/编辑器/Git/终端、右侧 DSH 原生对话。

![DSH 工作台布局：文件目录、编辑器与原生对话](https://raw.githubusercontent.com/TerryPro/dsh-vscode-panel/main/assets/workbench-files-and-chat.png)

![DSH 工作台布局：Git 更改视图、左右对照 Diff 与原生对话](https://raw.githubusercontent.com/TerryPro/dsh-vscode-panel/main/assets/workbench-git-diff.png)

## 项目由来

DeepSeek Harness（DSH）Web 是一个 AI 编程助手客户端，官方 AppFrame 以对话为中心。它出厂时并没有能配合对话使用的代码工作台——没有文件目录、没有编辑器、没有 Git 面板、也没有终端。

本插件的目标就是**以增量方式**补上这块能力。它不 fork、也不替换 DSH 的界面，而是注册进客户端公开的 slot（侧栏底栏、侧栏工作区区域、右侧会话列），把现有 AppFrame 重排成一套 VS Code 风格的三栏工作台。原生对话、任务状态、工具与输入框都保持 DSH 原样——这个项目最早只是给 DSH 做一个「类 VS Code 面板」，如今已从最初朴素的三栏布局成长为一个完整的编辑环境。

它是一个「双半」结构的插件：

- **宿主半（Node）**——挂载在 DSH Web 服务器上的可信 JSON 接口。它提供工作区文件操作和一个加固过的 Git 命令层，并按需托管 Mermaid 运行时包。每个请求都会校验来源，并被限定在官方工作区 id 与工作区相对路径之内。
- **客户端半（React）**——浏览器 UI。它渲染侧栏、编辑器、Git 视图、终端和各类结构化视图，且只与宿主接口通信。凡官方客户端暴露能力之处，都复用 DSH 组件与设计变量，因此工作台观感与交互都是原生的。

本版本针对 DSH Web 0.2.0-rc.2 构建并测试；peer 范围同时接受 0.1.5-rc.1，两者的侧栏、右栏与底栏 slot 契约一致。

## 概览

| 区域 | 提供的功能 |
| --- | --- |
| 左栏 | 会话、文件目录、Git 更改与提交图、终端列表、内核管理器 |
| 中栏 | 多标签、多窗格编辑，Markdown/Mermaid/HTML/CSV/JSON/图片查看器，`.ipynb` 笔记本编辑与执行，单文件 Diff，交互式终端 |
| 右栏 | DSH 原生对话、任务状态、工具与输入框 |

文件、Git 状态、编辑器标签和终端跟随所选**工作区**；聊天仍由当前**会话**管理。布局、图标、颜色、菜单、弹窗、悬浮提示和响应式行为都会在官方客户端提供能力时优先复用 DSH 组件与设计变量。

## 功能

### 文件与编辑

- 按需展开目录，并支持新建、重命名和删除文件或文件夹。
- 文件目录和中栏标签使用工作区 Git 状态着色：未跟踪、删除或冲突为红色，新增为绿色，修改和重命名为警告色；未跟踪状态只装饰文件本身，目录聚合其他后代状态中优先级最高的一项。
- 在同一标签栏打开多个文件；标签溢出时可在顶栏使用滚轮横向滚动。
- 右键任意标签打开 VS Code 风格菜单：关闭、关闭其他、关闭右侧、关闭已保存、全部关闭，保存、还原文件，复制路径、复制相对路径、在文件目录中显示，以及向右/向下拆分。批量关闭会逐个保留未保存草稿的确认弹窗；鼠标中键同样关闭所在标签。
- 使用 `Ctrl/Cmd + S` 保存当前文件。写入会检查 DSH 文件版本，避免静默覆盖外部修改。
- 页面可见时约每秒批量检查已打开文件；从其他软件切回页面时立即检查。未编辑的标签会自动更新，未保存草稿遇到外部修改时会提示选择重新加载或保留当前内容。
- 编辑器按 CodeMirror 的规范化文本比较修改状态，并在保存时保持文件原有的 CRLF、LF 或 CR 换行风格，避免仅因换行格式产生黄色未保存标记。
- 在文件右键菜单复制工作区相对路径或绝对路径；将 DSH 工具产生的文件索引直接打开到中栏。
- 同一份菜单里可以在系统文件管理器中显示任意文件或文件夹：由宿主把相对路径解析为实际位置，再以参数数组（不是 shell 命令行）交给 Explorer、`open` 或 `xdg-open`；没有已知文件管理器的平台会直接说明，而不是点了没反应。
- 依据文件路径解析语言并提供 24+ 种语法高亮——C/C++/C#、CSS/SCSS/Less、Go、HTML/Vue、Java、JavaScript（含 JSX/MJS/CJS）、TypeScript（含 TSX）、JSON/JSONC/JSON5、Markdown、Mermaid、PHP、Python、Rust、SQL、Shell、Dockerfile、TOML、INI/`.env`、XML/XHTML、YAML 以及 CSV/TSV。状态栏显示解析出的语言；未知类型退回纯文本。
- 常见图片以渲染预览打开，而非原始字节；其他二进制文件显示二进制变更提示。

### 多窗格编辑

- 将中栏拆分为两个窗格，每个窗格有独立的标签条、状态栏和视图开关。
- 新文件打开到当前聚焦的窗格；可将任意标签跨窗格拖拽移动，目标窗格会显示柔和的放置区高亮浮层。
- 也可从标签右键菜单的“向右拆分/向下拆分”把该标签移入另一窗格并聚焦它；已分栏时这两项自动隐藏。
- 副窗格最后一个标签关闭后自动收栏。
- 终端同样参与分栏：可并排 `终端｜文件` 或 `终端｜终端`，运行中的终端在窗格间移动时不丢会话。

### 行内 Git 变更

- 源码编辑器将当前缓冲区与 Git `HEAD` 比较，在可点击的变更边栏中以绿色显示新增、蓝色显示修改、红色标记删除位置，不给代码内容铺设底色。
- 点击标记可打开带上下文、旧/新双行号、`-`/`+` 行及字符级变更强调的局部 Unified Diff，在变更间导航，或仅还原这一块（还原只修改当前草稿且支持撤销）。
- 拖动弹层右边缘可调整宽度，也可以聚焦边缘后用方向键微调；宽度会限制在当前视口内，并在切换变更、文件和刷新页面后保留。点击弹层之外会将其关闭。
- 已暂存、未暂存和尚未保存的编辑会合并呈现，并随输入、保存、外部修改和分支切换更新。Markdown 渲染预览保持干净，切换到源码后显示这些标记。

### Markdown

- Markdown 默认以渲染后的预览模式打开，也可切换到源码编辑；分栏视图同时展示两者并同步滚动。
- 可按文件标签切换右侧大纲（目录）面板，预览与分栏模式均支持；点击标题会将预览平滑滚动到对应位置。提取大纲时会跳过围栏代码块并剥离行内标记。

### 结构化数据：CSV/TSV 与 JSON

- **CSV/TSV 表格查看器**：带冻结行号列、顶部筛选工具栏（跨所有单元格的大小写不敏感子串匹配 + 实时匹配计数）、列排序，以及能识别数字/日期/文本列并给出求和/最小/最大/均值的汇总页脚行。
- **表格模式下的编辑**：单元格就地编辑、相对活动单元格的插入/追加/删除行列、双击表头改名、`Ctrl+V` 按当前分隔符解析的区域粘贴；并有撤销/重做（`Ctrl/Cmd + Z`、`Ctrl/Cmd + Shift + Z`）和按文件持久化的列宽。所有编辑走与文本文件相同的版本校验草稿/保存管线，保留换行风格、尾随换行与 BOM。
- **JSON 查看器**：面向 `.json`/`.jsonc`，由自研零依赖、带源码偏移的解析器驱动，容忍注释、尾随逗号与不完整输入。四种视图——可交互的节点连线**图**画布（缩放、平移、可折叠卡片、点击定位）、缩进**树**（搜索保留祖先链、大数组按每页 200 条分页、展开/折叠预设按文件持久化）、将结构化窗格与源码编辑器联动的**分栏**视图，以及原始**源码**。文档大小与深度都有上限，保证超大文件依旧流畅。
- 两个查看器都在状态栏一枚开关下提供 表格/树、分栏、源码 三态，并按视图记住分栏比例。

### 图表与文档：Mermaid 与 HTML

- **Mermaid** 文件（`.mmd`/`.mermaid`）实时渲染为 SVG，做了防抖且只保留最新一次编辑，支持放大/缩小/适应/重置缩放、跟随明暗主题，报错信息会指出出错行。运行时包由宿主托管、按需加载。
- **HTML** 文件（`.html`/`.htm`/`.xhtml`）以预览打开，有三态：**静态**（锁定的 `sandbox=""` iframe + 严格 CSP，永不执行脚本）、**交互**（可运行脚本的不透明源沙箱，运行时把相对路径的 `.js`/`.css` 依赖自动打包为 blob URL，受单文件与总量大小/数量限制）、以及**源码**。编辑草稿会实时反映到预览。

### 笔记本：`.ipynb` 编辑与执行

以 VS Code 的 Jupyter 插件为参照，但按本工作台的规则实现，而不是内嵌一个 Jupyter 前端。

- **单元格编辑。** 新增、删除、移动单元格，就地编辑任意单元格，并可用单元格自己的类型下拉在代码与 Markdown 之间切换。原始文本（Raw）不作为可创建的单元格类型提供，但文件里已有的 raw 单元格仍会如实标成"原始文本"，而不会悄悄显示成"代码"，也可以被转换出去。每个代码单元格带有 Jupyter 的提示序号（`[ ]`、运行中 `[*]`、完成后 `[12]`）——而且只有代码单元格有：给 Markdown 单元格标上序号，等于宣称它还有活儿没干完。Markdown 单元格就地渲染，用单元格上的编辑/渲染按钮（或双击、`Esc`）在源码与渲染之间切换。编辑是对笔记本 JSON 的结构化修改，与普通文件共用同一套“版本校验草稿—保存”管线，因此保存、脏标记、外部改动提示、还原全部与文本文件一致——一次运行产生的输出也会像 Jupyter 自己保存的那样写回文件。
- **真正的内核，零原生依赖。** Host 自己实现了 Jupyter 消息协议：TCP 上的 ZMTP 3.0、NULL 握手、HMAC-SHA256 签名，以及 DEALER/SUB 通道，全部用纯 Node 写成。不需要 `libzmq`、`node-pty` 或任何编译步骤，客户端包里除笔记本视图本身外不新增任何浏览器依赖。
- **Windows 上真正能用的中断。** ipykernel 自己的 `interrupt_request` 在 Windows 上是空操作，因此内核由一个只依赖标准库的 Python 桥接进程启动：它创建 ipykernel 所等待的 Win32 事件并在需要时触发。同一个桥接进程也持有内核轮询的父进程句柄，这保证了内核进程绝不会比 DSH 宿主活得更久——已通过杀掉宿主、确认端口随之关闭来验证。
- **内核发现。** 优先使用工作区自己的 `.venv`/`venv`/`env`/`.conda`（并向下扫一层目录以适配 monorepo），其次是 `py` 启动器、`PATH`、`uv` 托管的解释器，最后是已安装的 kernelspec。每个候选都会被**实测**——回报版本以及能否 `import ipykernel`——而不是凭猜测；kernelspec 会按它自己 `argv` 里写的解释器来探测，所以装在 `PATH` 之外的前缀里的内核同样能启动。选择器会列出不可用的内核并说明原因；插件绝不自行安装任何东西。
- **打开即连接。** 打开笔记本会自动扫描工作区并启动最合适的内核——优先用文件自己声明的 `metadata.kernelspec`（只要它在这里能启动），否则用工作区自己的环境——所以还没运行任何东西，状态点就已经是绿的，与 VS Code 一致。工作区没有可用内核时不会去启动任何东西（改由选择器说明原因），后台标签页也不会被探测，因为只有正在显示的笔记本才会挂载。
- **状态栏也会报告内核。** 工具栏会写出内核名字，但它只存在于笔记本视图——把标签切到源码，文件就变成一份普通 JSON，而它的内核仍在后台运行，屏幕上却没有任何地方说明这件事。状态栏在两种视图下都给出这条读数：名称与状态点（在笔记本视图里它把名称让给工具栏，只补工具栏从未给过的信息）、提示序号 `In[12]`、一次"运行全部"还欠多少个单元格，以及——一个此前在任何界面上都没有出现过的事实——事件流降级为轮询的那一刻，并用告警色标出，因为它比阅读者预期的更慢。
- **一个笔记本一个内核。** 同一文件的第二个标签页共享其命名空间，冷启动竞态只会产生一个进程；关闭标签页会释放浏览器侧的事件流但让内核继续运行，以便用户立刻重开时变量还在——由 Host 的闲置回收计时器负责收尾，与终端遵循同一策略。重启会换掉整个会话并给出新 id，因此任何事件流都不可能被要求回放一个已不存在内核的输出。从选择器里挑一个与自动连接**不同**的内核会干净地替换掉当前的，所以选择器不会形同虚设。
- **像终端一样可读的输出。** 文本流按块合并，而不是每次 `print` 一行；ipykernel 带 ANSI 颜色的 traceback 被渲染出来而不是露出控制码；MIME bundle 取最丰富的形式绘制（`image/png`、`image/jpeg`、`image/gif`、`image/webp`、`image/svg+xml`，其后是 HTML、LaTeX、JSON、Markdown，`text/plain` 兜底），因此 `pandas` 的数据框显示为表格、matplotlib 的图显示为图片。`tqdm`/matplotlib 的 `update_display_data` 就地重绘，不会堆出上百份副本。停在 `input()` 上的单元格会给出输入框，回答后继续。单元格只在真有内容可报时才长出输出区——从未运行的单元格什么都不显示，而运行过却什么都没打印的单元格会说明这一点，因为"没有输出"本身就是结果。
- **看得见也不会丢的输出。** 事件按内核单调编号，因此断线的 `EventSource` 会从自己的游标处续读并补齐缺口；在无法保持长连接的环境里，同样的帧由轮询接口送达。若游标已早于 Host 缓冲区的起点，会明确报告需要重建，而不是伪装成一次安静的运行。刷新页面不会打断正在执行的单元格。
- **安全边界。** 内核 HTML 是渲染目标而不是可信标记：脚本、事件属性、框架指令、远程资源与 `data:text/html` 在进入 DOM 前一律剥离。除 DSH 的回环/来源校验外，每个内核都持有启动时生成的令牌，因此同一台机器上的另一个页面既读不到某个笔记本的输出，也无法打断它的执行。路径、端口、密钥都不会离开 Host；输出按单次分块与单次运行双重限流，超限时会在单元格里写明。
- **快捷键。** 工具栏最左是保存按钮，文件有未保存改动时它会高亮（干净状态下不会禁用，免得"已保存"被误读成"按钮坏了"）；`Ctrl/Cmd+S` 与其它文件一致照常保存。`Ctrl/Cmd+Enter` 与 `Shift+Enter` 运行当前单元格，`Ctrl+Alt+Enter` 运行并在其下方新建一个，`Ctrl+Shift+Enter` 运行全部，`Esc` 退出文本单元格的编辑态并重新渲染——它就是单元格上"编辑/渲染"按钮的键盘版本。从文件树新建的笔记本是个空文件，加入第一个单元格时会写出一个合法的 nbformat 文档。

`examples/python_data_analysis/sales_notebook.ipynb` 是上面这些能力现成的导览：它读取同目录的 CSV，修正那份数据里刻意留下的缺失与负值，把汇总渲染成 `text/html` 表格，最后以一个会失败的单元格、一个向 stderr 输出的单元格，以及一个专门用来被中断的长任务收尾。

`examples/isolation/notebook-A.ipynb` 与 `notebook-B.ipynb` 是一对用来验证"两个笔记本会不会互相影响"的文件。它们**故意放在同一个目录**——同一个工作目录、同一块磁盘——并使用**同名**的变量（`marker`、`shared`、`count`）和**同名**的内存模块，只是值不同。把两个都打开、以任意顺序运行：只要有任何一格读到了对方的状态，断言就会立刻失败；两边各有一格去读对方的变量名，那一格必须报 `NameError`。中断与停止也都在对方仍在运行时验证。注意什么**没有**被隔离：两个文件共享目录，所以一方写到磁盘上的文件另一方读得到，这是正确的——这里的隔离指内核状态。

### 内核管理器

第五个侧栏模式，列出本工作区正在运行的全部内核。

- **显示什么。** 每一行给出所属笔记本、背后的内核、状态（执行中 / 就绪 / 启动中 / 失败）、已执行次数、有几个页面在看、已无人查看多久，以及操作系统进程号。顶部还有一行容量信息，报告本工作区与整个宿主的占用并在到达上限时告警——因为"内核启动被拒"原本只是一条干巴巴的报错，看不出是谁占着名额。
- **回收无人看管的内核。** 关闭笔记本标签是**故意**保留内核的，这样重新打开时变量还在；但这也意味着在被闲置计时器收掉之前，这个内核从任何地方都够不着。本面板就是那个"任何地方"：它可以停掉一个没有任何页面在看、且已超过宽限期的内核，而且不需要令牌——因为确实没有东西还在等它。
- **碰不到活跃笔记本。** 列表从不携带内核令牌；有页面连着流的内核根本无法在此回收，那一行只会提示"去它自己的笔记本里停止"。所有破坏性内核操作仍然要求打开它的那个笔记本的令牌，所以本面板无法打断、注入代码、或读取一个它只是"看得见"的笔记本。刚刚才无人查看的内核也会被短暂拒绝，因为一个正在刷新的页面和关闭标签在瞬间是同一个样子。

### SQL 笔记：在 `.sqlnb` 里查数据库

第二种笔记本格式，用来查工作区里的数据库。只借 `.ipynb` 单元格视图的视觉语言，别的都不共享：没有内核、没有 Python、没有任何要装的东西。

- **零安装。** SQLite 就跑在宿主自己的进程里，所以一份 `.sqlnb` 不需要解释器、不需要驱动、不需要 `pip`——你和一条查询之间只隔一个数据库文件。文件由宿主打开、用 authorizer 围起来、再把行流回来看。
- **三个入口。** 文件树的「新建 SQL 笔记」建一份空的；双击 `.db` / `.sqlite` / `.sqlite3` 会在旁边建一份，第一格已经写好列出这个库的表，并连到这个文件上；右键的「在 SQL 笔记中打开」同理。从零建的那份接内存库，所以不用先选文件就能跑。
- **单元格。** 一格一行，行头给出类型（SQL 或文本；某个更新的格式写的类型会当只读文本显示，不会拿去当 SQL 跑）、`In[n]` 序号、耗时和结果块。可以跑一格、按文件顺序跑全部（遇错就停，并说明停在第几格）、取消、清空输出。拖行头可以重排，折叠会把正文和结果收到行头后面，大纲列出文本格的标题。
- **笔记记得住。** 一格的运行结果——列名、声明类型、数据行、它跑在哪个 `In[n]`、花了多久——会在运行结束时连同这份笔记连的库与档别一起写进 `.sqlnb`。重开文件就会重新连上那个库，并直接显示记下的答案，而不是一份要重跑一遍的空笔记。结果是跑完即存的，所以它在文件里、不在一个需要你记得保存的草稿里；本工作台不允许改写的文件会在运行前就说明"结果只留在屏幕上"。这次改动之前写的文件（版本 1）照常可用，首次写入时自动升级。
- **结果。** 一格里的每条语句各出一张表，表头第二行是声明类型，二进制值写 `BLOB · 1.2 KB`；三种情况不会看成一回事：NULL 显示 `∅`，空串显示 `·`，四个字母的文本 `NULL` 就是 `NULL`。超过行上限的行会被说明，而不是默默丢掉；被截断的块会先留出分页的位置。
- **连接归笔记所有。** 一份笔记一个连接，同一份笔记的两个标签共享它的临时表。侧栏列出工作区里的库（`-wal`/`-shm` 是库留下的伴生文件，不是库，不列），按需展开连接到的那个库的表、视图和列，双击一张表就会把它的 `SELECT *` 写进一个新格。
- **默认只读。** 不显式选可写档就是只读连接；一个文件同时只允许一个可写连接，另一份笔记来要会被拒并说明原因，而不是共享句柄、让一份笔记的写入意外到另一份头上。
- **状态条会报**，单元格视图和源码视图都报，所以哪怕文件正被当裸 JSON 看，也能看出这份笔记连着哪个库。
- **快捷键与 `.ipynb` 笔记一致：** `Ctrl/Cmd+Enter` 与 `Shift+Enter` 跑当前格，`Ctrl+Alt+Enter` 跑完在下面新开一格，`Ctrl+Shift+Alt+Enter` 跑全部，`Ctrl/Cmd+S` 保存。

有三条边界，依赖它之前先知道：

- **停不下来。** 取消会停掉还没开始的格，并让正在逐行取回的查询在下一批行处停下；但代价全落在第一行的语句——聚合、写入——会跑到底。按钮上写的正是这一点。
- **WAL 伴生文件。** 只读打开一个 WAL 库，第一条语句就会在它旁边生成 `-wal` 与 `-shm`，关闭连接不会删掉它们；只有最后一个可写连接干净关闭才会清。这里选择接受这个事实而不是绕开，因为绕开的代价是读到旧快照还不说。
- **一条语句只碰一个库。** `ATTACH` 在两档都被拒，所以一条查询到不了这份笔记没连的文件。

### Git 工作区

- 以列表或目录树查看已暂存和未暂存更改。
- 通过明确操作完成暂存、取消暂存、放弃更改和提交；长文件名在静止时使用整行宽度，文件行悬浮后再按一个或两个按钮的实际宽度收缩，直接悬浮按钮时显示圆形底色。
- 将工作区、暂存区、历史提交或比较结果中的每个文件作为独立 Diff 标签打开。
- 使用 CodeMirror MergeView 渲染文本 Diff，包含行号、字符级变更、未修改区域折叠、左右对照/统一/行内三种始终可选的模式和长行换行。
- 从本地与远程引用构建轨道式提交图，展示分支、合并、标签、作者、时间和文件统计；滚动时自动按每页 40 条加载更早提交。
- 在原位置展开提交，按列表或目录树排列文件，并逐个打开。
- 创建、切换、重命名和安全删除本地分支，也可从指定引用或提交创建分支。
- 管理远端，并针对上游或明确指定的远端与分支执行 Fetch、快进 Pull、Push、发布分支和同步。
- 在提交菜单中复制提交号、Cherry-pick、Revert、创建分支或与当前工作区比较。

### 终端

- 通过 DSH **官方**终端服务（`@deepseek-ai/dsh-api-terminal-controller` 与宿主的 `webTerminals`）运行交互式 xterm.js 终端，不再自带任何需要本地构建的原生模块。插件侧只是一个薄薄的模拟器，进程派生、传输和屏幕恢复都由 DSH 负责。
- 传输走 Gateway Remote 流——Web 配置下为 WebSocket 多路复用，桌面端为 IPC 桥接。
- 终端标签属于**工作区**：切换标签保留屏幕，切换工作区或会话同时保留标签**和进程**。宿主按需解析任意会话的 Agent，因此标签始终通过为它派生进程的会话来驱动，工作区移开后也不会断开——切换会话不会再让终端失联。完全没有会话可寻址的标签显示**尚未分配会话**（空心状态点），而不是假装在运行。
- **为终端命名。** 行上的铅笔操作可重命名终端，名字会作为终端自身的标题推送到宿主，因此名称由**进程**承载，而不只是本窗口的标签。命名后的终端在侧栏行、折叠轨道、编辑器标签栏和无障碍标签中显示同一个名字；未命名的回落到 `终端 N`。
- **每个终端报告自己的进程。** 行下方的状态栏镜像宿主确实报告的事实：进程解析出的 Shell（恢复的终端同样适用）、PTY 网格，以及**启动**目录。宿主明确说明 shell 切换目录不会更新该字段，因此这里标注为启动目录，而不是假装在跟踪 `cd`。进程退出后还会报告退出码。
- **聚焦的终端在底部也报告同样的事实。** 终端窗格下沿新增一条状态栏，高度、分隔线、底色与字号都和编辑器状态栏完全一致，因此在文件与终端之间切换不会让窗格底边跳动。它以相位与状态点开头，随后是 Shell、网格、启动目录（去掉标签，标签移到悬浮提示），进程结束后把退出码钉在最右侧。两处表面共用同一套词汇解析，所以状态栏、侧栏行、标签与轨道圆点不可能对同一个终端各说一套；宿主尚未报告的事实直接不显示，而不是摆一个占位符。
- **为每个终端选择 Shell。** 新建终端按钮列出宿主在当前会话执行环境中验证过的 Shell——PowerShell（`pwsh` 与 Windows PowerShell）、CMD、`bash`、`zsh`、`fish`——终端行随后显示进程实际解析出的 Shell。选择结果同时记为本浏览器的默认值，因此工作台与 DSH 自带终端遵循同一偏好。不做选择时使用宿主默认：Windows 取 `ComSpec`，类 Unix 系统取 `SHELL`；恢复的进程始终沿用它启动时的 Shell。

### 对话与布局

- 右栏继续使用 DSH 原生对话和输入流程。
- 沿用官方 AppFrame 分隔线行为调整中栏与右栏宽度；右栏默认宽度随窗口变化，大屏下可继续向宽处拖动，同时为中栏保留可用空间。
- 可从左侧活动栏收起中栏；选择文件、Diff 或终端时会自动重新展开。对话栏收起开关并列在同一条活动栏上，即使中栏关闭，两个开关也都能点到。
- 收起中栏会把 DSH 的**原生右侧栏**交还给你。工作台编辑器挂在官方的右栏席位（`rightbar.session`）上，而该席位只容得下一个占用者，因此只要占着它，原生右侧栏就必然被遮蔽——它的停靠面板、引导页标签、自己的分隔线，以及宽度上报都在内。入口就是 DSH 对话头部那枚**展开右侧栏**按钮：点它即收起中栏并释放席位，于是 DSH 正要绘制的面板终于有人绘制；重新展开中栏则收回席位。切换过程不丢东西：已打开的标签、终端与笔记本内核都还在——卸载的终端会重新挂回同一个官方模型，标签消失也从不中止内核。
- 左栏底部保持 DSH 原生的上下排列：其它插件贡献的控件（例如额度读数）继续排在账户/设置行的上方，不会被挤到同一行里。
- 打开官方或第三方插件注册的**全局面板**（如「插件」页、Qoder 额度页）时，面板按 DSH 的设计显示在右栏，中栏继续显示已打开的文件，不会变空或被覆盖；关闭面板即恢复对话栏。
- 用**返回会话**控件退出任意全局面板。DSH 自己的侧栏面板行只会*选中*面板——它的处理函数是 `selectPanel(id)`，从不调用 `selectPanel(null)`——因此当工作台接管会话列表后，官方界面里没有任何能离开面板的控件。在「插件」页上，它并入该页自身的头部动作区（刷新与添加）；对其它面板、以及插件页的详情页，它出现在活动栏视图图标下方。任何时刻只会出现一个，常驻图标簇也不会位移。
- 可拖动左侧侧栏在受限范围内调整宽度；侧栏与中栏之间保留可见边界线，菜单栏下方也有分隔线。
- 即使工作区会话还没有消息，也能访问该工作区的文件与 Git。
- 对话栏变窄时会适配输入工具栏、菜单、失败信息和助手消息统计。
- 收起中栏后，对话会回到官方中间位置和原始表面颜色。

## 安装

将公开包安装到 DSH Web 配置：

```sh
dsh plugin --profile web add @lsq64737/dsh-workbench-layout
```

如果 DSH Web 正在运行，请在安装后重启。

终端复用宿主自带的终端服务，因此没有需要批准或构建的原生模块（例如 `node-pty`）——凡 DSH 内置终端可用之处，本插件终端都可用。

再次执行相同的 add 命令即可更新。卸载命令：

```sh
dsh plugin --profile web remove @lsq64737/dsh-workbench-layout
```

## 基本使用

1. 选择一个 DSH 工作区。
2. 使用左栏模式切换会话、文件、Git、终端和内核。
3. 选择文件、Diff、提交文件或终端，将其打开到中栏；对 Markdown/CSV/JSON/Mermaid/HTML 文件，可用状态栏开关在结构化视图、分栏和源码之间切换。
4. 打开 `.ipynb` 即以单元格方式编辑。笔记本一打开就会自动为该工作区连接最合适的内核；用 `Ctrl/Cmd+Enter` 运行当前单元格，或使用“运行全部”。内核选择器会列出可用项以及不可用的原因，也可以用它切换内核。
5. 拖动中栏与右栏之间的分隔线，调整编辑区和对话区宽度。
6. 使用左侧活动栏收起或恢复中栏与对话栏。

Git 功能要求所选工作区根目录本身就是 Git 仓库。远端操作使用运行 DSH 的机器上已经配置好的 Git 凭据；插件不会索取或保存远端凭据。

笔记本执行需要一个可从该工作区访问、且已安装 `ipykernel` 的 Python 环境。插件只负责启动并与之通信，绝不会自行安装环境。

## 配置

打开 **设置 → 工作台布局** 即可看到全部配置项的表单，每一项都显示当前值、默认值，以及宿主接受的取值范围。应用修改会重启本插件，而重启会停止本插件管理的所有笔记本内核，因此页面会先要求确认。同样的值也可以直接写进 profile 的 `cordis.patch.yml` 中本插件的 `config:` 块，在下次启动 DSH 时生效。

下面的表格是简版：什么值得改，以及调高它的代价。

| 配置项 | 默认值 | 约束的是什么 |
| --- | --- | --- |
| `maxFileBytes` | 2 MiB | 可打开或保存的最大文件。更大的文件只报告大小而不加载。 |
| `maxDirectoryEntries` | 1000 | 文件树每层列出的条目数。 |
| `gitTimeoutMs` / `gitMaxOutputBytes` | 30 秒 / 4 MiB | 单次 Git 操作的耗时与输出上限。 |
| `gitGraphPageSize` | 40 | 提交图每页的提交数。滚动会继续加载，所以这只决定一次到达多少条。 |
| `kernelStartTimeoutMs` | 60 秒 | 内核打开端口可花的时间。conda 环境或首次大量导入时调高。 |
| `kernelRequestTimeoutMs` | 15 秒 | 补全与悬停信息的回复，这类请求不应拖住界面。 |
| `kernelMaxPerWorkspace` / `kernelMaxTotal` | 3 / 8 | 内核数量上限。每个内核是一个 Python 进程，所以这两项省的是内存，不是整洁。 |
| `kernelUnattendedTimeoutMs` | 15 分钟 | 笔记本被关闭后内核还能活多久。想更久保留变量就调长它。 |
| `kernelReclaimGraceMs` | 5 秒 | 内核管理器允许回收一个失联内核前的等待时间——正是这段时间区分了"关闭标签"与"正在刷新的页面"。 |
| `kernelReaperIntervalMs` / `kernelHeartbeatMs` | 30 秒 / 15 秒 | 回收扫描间隔与事件流保活。中间的代理会掐掉安静连接时，调小保活。 |
| `kernelFrameBuffer` | 2048 | 每个内核为重放保留的事件数，也就是一条断线的流能补回多少输出。 |
| `kernelMaxOutputChunkChars` | 128 KiB | 单个输出块的上限，超出即截断并标注。 |
| `kernelMaxOutputRunChars` / `kernelMaxOutputRunFrames` | 4 MiB / 20 000 | 单个单元格一次运行的输出总量，超出即丢弃并给出一行 stderr 提示。 |
| `kernelDiscoveryCacheMs` | 60 秒 | 一次内核扫描结果的复用时间。装好 `ipykernel` 后若仍提示不可用，设为 0 强制每次重探，或重启内核。 |
| `kernelProbeTimeoutMs` | 8 秒 | 单个解释器回答"能否作为内核"可花的时间。 |

任何数字都不重复声明：设置页的数值直接读自活的 schema，文案读自 schema 构造自身描述所用的同一张表，有一条测试把每个默认值钉在宿主模块使用的那个常量上，字段列表还是有类型的——新增一个配置项却不给它安排位置，编译就过不去。设置界面显示一个数、代码执行另一个数，比没有设置界面更糟。

## 安全与隐私

- 宿主接口只解析官方工作区 id 和工作区相对路径，不接受浏览器提供的绝对路径作为文件目标。
- 拒绝访问工作区外路径和符号链接。
- 新建文件采用原子写入，保存检查版本，重命名不会主动覆盖已有项目。
- 外部文件刷新通过官方 DSH 文件系统批量比较版本；有未保存草稿时不会自动替换内容。
- 递归删除文件夹和破坏性 Git 操作需要确认。文件与文件夹删除是永久操作。
- Pull 和同步只允许快进；Cherry-pick 与 Revert 要求工作区干净，Git 报告冲突时会自动中止。
- Git 命令使用固定参数且不经过 Shell，并禁用 Git 操作中的终端凭据提示。
- 在系统文件管理器中显示条目时，宿主以固定程序加单个参数启动它——不经过 Shell，也不拼接命令行——目标路径由宿主自己从工作区相对路径解析得到，且响应与日志都不会重复它打开的绝对路径。
- HTML 预览运行在沙箱 iframe 内；交互预览运行在不透明源（opaque origin）沙箱中，不获得同源权限，且只打包受大小限额约束的相对资源。
- 内核输出的 HTML 在进入 DOM 前会先过滤，移除脚本、事件属性、框架指令、远程资源与可执行的数据 URL。
- 每个内核带有启动时生成的令牌，宿主接口在 DSH 的回环/来源校验之外再校验它；路径、端口与签名密钥都只留在宿主侧。
- 内核由宿主按工作区派生，受“单工作区数量”和“单进程总量”双重上限约束，无人查看且空闲的内核会被自动停止；笔记本文件本身只由编辑器的版本校验保存路径写入。
- 日志使用工作区 id 和相对路径，不记录宿主文件路径。
- 终端意味着可以操作运行 DSH 的机器，因此只应向你信任的用户和网络开放 DSH Web。

## 已知限制

- 已打开标签和未保存草稿只存在于当前页面，刷新后会丢失；终端进程由宿主保留，但本插件不会自动重建其标签。此时该进程约在两小时空闲后被宿主自动回收（`unattendedTimeoutMs`，默认 7200000 毫秒），重启 DSH 则立即释放。
- 文件编辑器只读取文本；图片以预览渲染，其他二进制文件只显示二进制变更提示，不渲染内容。
- 关闭终端标签会结束其进程；刷新页面保留进程但会丢失未保存草稿与其他标签。每个会话的终端数量受宿主 `maxTerminals`（默认 8）限制，且**已退出的终端仍计入该额度**——被会话切换留在原会话的终端同样占用原会话名额，关闭不用的标签才会释放。宿主或会话卸载时其终端一并结束。可用性与并发数遵循宿主自身的终端配置。
- DSH 目前没有公开的对话栏位置 API，因此插件通过官方 AppFrame 的稳定标记调整列顺序。未来 AppFrame 重构后可能需要同步更新插件。
- 工作台编辑器与 DSH 原生右侧栏无法同时出现在屏幕上：官方右栏只有一个会话级席位（`rightbar.session`），占用者由 slot 遮蔽规则选出，而不是并列堆叠。收起中栏就是切换的方式——编辑器的标签都还开着，原生右侧栏则带着它自己的标签、分隔线与布局回来——所以两者是同一列里的两种替代状态，而不是并排的两列。
- 结构化查看器对超大 CSV/JSON 设有大小、节点和深度上限以保证流畅；超出上限的内容会以源码或截断形式展示，而非完整渲染。
- 笔记本按 `.ipynb`（nbformat 4）工作，目前只启动 Python 内核；其他语言的内核会连同原因一起列在选择器里，但不会被启动。旧的 nbformat 3 或内容不是 JSON 的文件会给出说明，并可切到源码视图修正。
- 关闭笔记本标签不会立刻结束内核，因此变量在误关后可以找回；无人查看且空闲的内核由宿主计时器回收，重启 DSH 则全部释放。`text/html` 输出会被过滤后再渲染，因此依赖脚本的第三方富组件（如部分 `ipywidgets`）只显示其文本兜底。
- 在 Windows 桌面版中，收起后的侧栏宽度为零，DSH 会隐藏侧栏的浏览区和底栏；此时模式切换与中栏开关不可用，重新展开侧栏即可恢复。macOS、浏览器和 Linux 下收起侧栏仍保留图标栏，两个控件都可继续使用。
- 窗口非常窄时，AppFrame 官方让步规则会暂时关闭中栏，宽度恢复后再自动打开。

## 开发

需要 Node.js 24 或更高版本，以及兼容的 DSH 开发工作区。

```sh
npm ci
npm run typecheck
npm test
npm run build
npm run test:bundle
npm run test:kernel     # 可选：笔记本内核的端到端验证
npm run test:example    # 可选：逐格执行示例笔记本
npm run test:isolation  # 可选：证明两个笔记本互不影响
npm run test:sql        # 可选：SQL 笔记门禁，跑在 DSH 宿主 runtime 上
```

`npm run typecheck` 除了插件源码，还检查模拟 DSH 快照的测试桩（`workspace-binding`、`workbench-sidebar`、`workbench-editor`）以及笔记本相关测试：宿主类型变更会直接让构建失败，而不是静默关掉这些检查。部分其余测试文件暂未做类型检查。

`npm run test:sql` 分两层报告。**事实层**在插件真正运行的那个 runtime——DSH 宿主内嵌的 Node，不是 PATH 上的 Node——上量 `node:sqlite` 的行为，必须常绿：任何一条翻转，就说明 SQL 笔记建立在一条已不成立的结论上，门禁会直接把这件事指出。**闸门层**断言的是 SQL 笔记的功能面（路由、`.sqlnb`、取消、可写占用）；某个里程碑尚未实现时，它对应的闸门为红是预期状态。它会用 `--host <路径>`、`DSH_HOST_EXE`、以及定位正在运行的 DSH 进程这三步找到宿主可执行文件并在其下重新执行自己；找不到就报错，而不是退回到 PATH 上的 Node 去量一个错的 runtime。

`npm run test:kernel` 会把**构建后**的宿主包挂载到一个最小模拟上下文中，再用真实的 `ipykernel` 通过 HTTP 驱动它自己的路由：内核发现、来源与令牌校验、断线后事件流补齐、轮询兜底、输出转换、Windows 上打断长单元格、两个笔记本各自独立的命名空间，以及收尾后不残留内核进程。它需要工作区可访问且装有 `ipykernel` 的 Python，因此没有被纳入 `npm test`。

`npm run test:example` 会把 `examples/python_data_analysis/sales_notebook.ipynb` 的每一格都过一遍真实内核，并报告每格的最终状态，这样随仓库发布的示例是被验证过的，而不是被假设的。`npm run test:isolation` 对 `examples/isolation` 那一对做同样的事，并且把"隔离"断言在**测试脚本自己伪造不了**的证据上：两个笔记本报出**不同的操作系统进程号**、各自读不到对方的变量、并且一方中断或停止时，另一方正在跑的单元格不受影响。

修改 `src` 后必须执行 `npm run build` 重建 `lib/client.js`，DSH 客户端加载的是构建产物而非源码，之后才会生效。同一次构建还会把 `src/host/kernel/kernel-bridge.py` 复制到 `lib/index.js` 旁边——Host 启动内核时正是到那里寻找它。
