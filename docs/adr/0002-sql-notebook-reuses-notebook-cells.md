# SQL 笔记复用笔记本的单元格视图，但不复用它的会话与传输

需求：SQL 笔记"要有类似 Jupyter 笔记的样式"。备选是新写一份精简的单元格列表只借视觉样式；以及把 SQL 做成宿主 `KernelSessionHandle` 的第二个实现，连会话机器一起复用。

决定：**只复用客户端的单元格视图**（单元格结构、拖拽、折叠、键盘导航、输出渲染与净化），传输与会话管理另起一组 `/sqlnotebook` 路由，不进内核 registry、不进左栏内核面板。理由：客户端这一半从不接触 Jupyter 线协议，所以复用视图的代价只是重审三个 Jupyter 专有语义；而复用会话机器则要背上为子进程设计的一整套东西——事件流、游标与环形缓冲、SSE 降级轮询、空闲回收——对一条跑完就返回的查询全无意义。

执行不能占住宿主主线程。实测：一条慢同步查询期间，同期一条真实宿主路由从 13ms 被拖到 4336ms，等于文件保存、Git、内核 poll 一起无响应；而行上限救不了聚合，因为聚合的全部时间落在结果的第一次取值上。分两期：**一期用惰性取行 + 分批让出事件循环**（同期路由降到 99ms），**二期换成一个连接一个 worker 线程**。

## Consequences

- 单元格视图是共用资产：改它要同时想清楚两个宿主（真内核 / SQL 后端）会不会一起坏。
- **实现注（A5 口径核对）**：实际落地的是“共用视觉语言与净化”，不是共用组件——`SqlNotebookSurface` 是独立的一份单元格列表，共用的是图标（`NotebookIcons`）、`MarkdownOutline`、`extractMarkdownOutline`、`sanitizeKernelHtml` 与结果表格的 CSS 词汇。原因：`NotebookSurface` 1476 行、配 1650 行 spec，且与内核运行时耦合，改它属于另一个已定下的取舍（A2 时选的是不碰）。代价是拖拽/折叠/键盘导航各有一份实现；若日后要合，合成点是在“单元格列表 + 每格一块视图状态”这层，不在运行时。
- 三个既有门禁与本模块无关，不要因为"看着像"就顺手接上：`language === 'python'` 的判定、argv 里没有已知 launcher 时静默换成 ipykernel、"每个笔记本一个内核子进程"的回收模型。
- 按 [GLOSSARY.md](../../GLOSSARY.md)：笔记本与 SQL 笔记是两个概念，共用单元格这一视觉语言，但文案键与 `language` 判定不许混用。
