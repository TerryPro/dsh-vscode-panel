# 筛选面可以重复，连接面不可以

需求：侧栏 SQL 面板要在笔记列表上方加一枚「数据库」下拉，用它把列表收窄到某个库的笔记。但这会让全应用同时存在**两枚数据库下拉**——中栏 `.sqlnb` 工具条上那枚（ADR 0008 明确划归它的连接控件）和侧栏这枚新的。

[ADR 0008](./0008-sql-ui-scope-split.md) 否掉重复控件时写下的理由是：「**两个长得一模一样的数据库下拉并列时，读者无法判断点哪个作数**」。

那么本决定是否推翻了 0008？不是。两枚下拉的动作不同：

| | 工具条那枚 | 面板这枚 |
| --- | --- | --- |
| 选完之后发生什么 | 改变这份笔记的连接目标，要再点「连接」 | 只改变列表可见范围 |
| 会不会打开或关闭句柄 | 会 | **不会** |
| 归属 | 中栏 `.sqlnb` 工具条 | 侧栏 SQL 面板 |
| 失效范围 | 当前笔记 | 当前面板的列表 |

## 决定

**同一个数据可以在两处出现，只要两处的动作不同；同一个动作不能出现在两处。**

0008 删掉的是**动作**的重复（两处都能「选库并连接」，读者不知道哪套作数）。本决定加的是一处**视图收窄**：它读同一份数据，但不对连接做任何事。判据因此从「这个数据出现在几处」改成「这个动作出现在几处」。

## Consequences

- **面板可以扫描工作区了**。0008 的第 26 条后果写「面板不再扫描工作区：那次遍历只为填库下拉，下拉走后面板没有东西可喂」，那条已被后续的笔记列表改动越过（面板现在为了列出工作区里的 `.sqlnb` 而扫描），本决定给它加了勘误注。新增的库列表不再是一次单独的遍历：笔记与库由**同一趟** BFS 收集（`sql-workspace-scan.ts`），所以"两处读同一份数据"在成本上也成立，而不只是说法上。
- **两条截断声明是分开的**。笔记与库各有各的上限与 `truncated`，因为"笔记列表完整而库列表被截断"是一种真实状态，一个共用布尔位必然对其中一份说谎。
- **筛选依据是笔记文件记录的库**（`explicitDatabase`），不是运行时当前连着的库。这样筛选结果与行上第二行永远同源——不会出现"筛进来了却显示未连接"。代价是：刚手动连上但尚未存盘的笔记，要重扫才会归到新库下。接受，因为另一个方向（按 live 连接筛）会让同一份列表的两处说法不一致。
- **筛选值不跨工作区**。它命名的是某个工作区里的一个库，跟着换个工作区就指向一个不存在的文件。
- **两侧措辞必须不同**。工具条那枚叫「选择数据库」，面板这枚叫「按库筛选」；面板复用前者的原话就会让两枚读成同一个动作，那正是 0008 要防的。
- **仍未修的一条既有缺陷**（0008 已记录，与本决定无关）：工具条的库下拉在连接后仍可改，而那个位置此刻是「断开」，于是下拉可以显示一个并未连上的库，同时读数显示实际连上的那个。

## Considered Options

- **让面板的下拉也能直接连接**：被否。那正是 0008 删掉的动作重复，两处各实现一遍"连接后不许换库换档""内存库没有档别"这类规则，任何一次遗漏都是一个界面遵守另一界面不遵守。
- **把库列表放进面板头部**：被否。面板头部是笔记列表与结构树共用的，放那里的控件读作"整栏的作用域"，而这枚只管列表。仓内既有判据（`ca2296c`）是**提示留在离它解释的东西近的那一处**，控件同理——它解释列表，就放在列表上。
- **不引入筛选，改用搜索框**：被否（本轮）。读者要回答的问题是"哪些笔记是 `demo.db` 的"，而不是"哪些笔记名字里含这几个字"；关联是这份文件里已经存在的事实，让读者手打库名是把已知的事实推回给人。
